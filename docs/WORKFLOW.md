# 개발 협업 방식

## 한 번에 한 작업

1. 사용자가 이번 작업의 플레이 목표를 정한다. 한 작업은 기능 또는 문제 하나로 제한한다.
2. Claude 또는 Codex 한 명이 해당 파일의 구현 담당자가 된다. 다른 한 명은 커밋을 검토하고 재현 테스트를 맡는다. 같은 파일을 동시에 수정하지 않는다.
3. 작업 요청은 아래 5줄만 보낸다. AI를 더 고용하기 전에 이 방식으로 중복 작업과 토큰 사용을 줄인다.

```text
목표: 플레이어가 무엇을 할 수 있어야 하는가
담당: Claude 또는 Codex
브랜치/기준 커밋: ccr-023f5a43-0sn456 / git rev-parse HEAD
수정 범위: 파일 또는 함수
완료 조건: 모바일 조작, 저장 후 이어하기, 콘솔 오류 없음 등
```

## 코드와 배포

- 수치와 업그레이드는 `prototype/balance.js`; 게임 규칙은 `prototype/game.js`; 화면은 `prototype/index.html`과 `prototype/style.css`에서 수정한다.
- 공개용 `gh-pages`는 `prototype/` 내용을 루트에 복사한 배포 브랜치다. 개발 브랜치와 함께 갱신하고, Pages 설정이 어느 브랜치를 보는지 확인한다.
- `main`은 아직 초기 README다. PR #2가 머지되기 전에는 `main`을 최신 게임으로 가정하지 않는다.
- 수정 전후 `git status`, `git log -1`, `git diff --check`, `node --check prototype/game.js`, `node --check prototype/balance.js`를 확인한다.
- GitHub Actions가 JavaScript 문법을 검사한다. 통과해도 모바일 조작과 실제 재미가 검증된 것은 아니다.
- 휴대폰 크기 브라우저에서 시작, 채집·판매, 눈보라, 저장·이어하기를 확인한다. 수치 변경은 `docs/GDD.md`와 `docs/PLAYTEST.md`에 기록한다.

## 다음 개발 순서

1. 사람 5명에게 10분씩 플레이를 요청해 첫 판매, 첫 업그레이드, 첫 눈보라, 이탈 시점을 기록한다.
2. 15개 목표가 끝난 뒤 할 수 있는 반복 선택을 설계한다. 우선 후보는 감시탑: 장작을 판매·난방·방어 중 어디에 쓸지 결정하게 한다.
3. 재미와 조작이 확인되면 Unity 이식 범위를 정하고 Android·iOS 실기기 빌드를 시작한다. 아트·사운드 전문가는 이때 필요에 따라 합류시킨다.
